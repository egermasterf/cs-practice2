git diff — показывает построчную разницу между рабочей директорией, индексом и коммитами.

git show — выводит содержимое одного коммита вместе с его изменениями относительно родителя.

git log — выводит список коммитов в обратном хронологическом порядке.

git log -S "строка" — находит коммиты, в которых изменилось число вхождений указанной строки.

git blame файл — показывает для каждой строки файла коммит, автора и дату последнего изменения этой строки.

git restore <файл> — берёт версию файла из индекса (staging area) и кладёт её в рабочую директорию. То есть «верни как было подготовлено к коммиту».

git restore --source=<commit> <файл> — берёт версию файла из указанного коммита/ветки/тега и кладёт её в рабочую директорию. То есть «верни как было в том коммите».

Что делает git revert

    Создаёт новый коммит, который отменяет изменения заданного коммита.
    Не удаляет исходный коммит из истории — он остаётся на месте.
    История становится линейной и прозрачной: любой разработчик видит и ошибку, и её отмену.
    Пример: если был коммит «Add division (intentionally without zero-check)», то git revert создаст коммит «Revert "Add division…"», который уберёт деление из кода.

Что делает git reset --hard

    Перемещает указатель ветки (HEAD) на более старый коммит.
    Удаляет последующие коммиты из текущей ветки — они перестают быть частью истории (хотя временно доступны через git reflog).
    Сбрасывает рабочую директорию и индекс к состоянию выбранного коммита, полностью удаляя изменения.
    Пример: git reset --hard HEAD~1 «стирает» последний коммит: его нет в git log, а файлы возвращаются к предыдущей версии.

Почему git revert безопаснее в опубликованной истории

    Не переписывает историю. В публичных ветках (например, main на GitHub) другие разработчики могут уже опираться на существующие коммиты. git reset меняет историю, и при попытке push Git заблокирует операцию или потребует force push, что опасно: у других участников репозитория могут сломаться локальные ветки.
    Сохраняет полный след изменений. Даже ошибочные коммиты остаются в истории — это полезно для аудита: можно понять, когда и почему была допущена ошибка и как её исправили.
    Избегает конфликтов при синхронизации. git revert добавляет новый коммит, который можно безопасно отправить через обычный git push. Другие разработчики просто подтянут изменения через git pull — без риска рассинхронизации.
    Поддерживает прозрачность командной работы. В совместных проектах важно, чтобы история была предсказуемой. revert позволяет любому участнику увидеть полную картину: ошибка → исправление.
